# Workflow

## Scope

本文件记录 UE5 项目开发的通用阶段工作流、文档分层方式、交付格式与同步规则。遇到“需要把一次开发沉淀成可复用路线”时读它。

## Four-Step Loop

### 1. Clarify

- 先明确为什么做、做什么、不做什么。
- 先讲验收口径：功能、视觉、性能、编辑器操作量。
- 对方向性需求，先列 2~3 条方案与权衡，等用户拍板。

### 2. Maintain a Main Design Doc

主设计稿只保留：

- 本期摘要
- 关键约束
- 公式或结构变化
- 跳转到详稿
- 状态

单期摘要尽量压在 12~30 行，不要把完整实现塞进主稿。

### 3. Split Detailed Stage Docs

遇到以下情况拆详稿：

- 新阶段
- 新系统
- 新模块
- 新材质通路
- 需要用户手工搭材质 / 蓝图 / DataAsset
- 未来大概率复用

推荐结构：

1. 一句话目标与边界
2. 架构 / 数学 / 数据流
3. C++ / Blueprint / HLSL 实现
4. 编辑器搭建步骤
5. 验收清单
6. 排错表
7. 与上下游关系
8. 附录：完整可粘贴代码与配置

硬规则：

- 提供最终可粘贴版本，不让用户自己拼。
- 每个已知坑都写成“症状 -> 根因 -> 修复”。
- 写清楚影响到的模块、资产、参数和日志。

### 4. Land and Verify

- 改完立即编译。
- 编译通过后立即更新主稿状态。
- 若还有编辑器手工步骤，给严格顺序清单。
- 验收通过后，把经验回写进文档。

## Main Doc vs Detailed Doc

### Main Doc Responsibilities

- 全局路线
- 阶段状态
- 跨阶段约束
- 风险表
- 资源表

### Detailed Doc Responsibilities

- 完整实现
- 节点级步骤
- 可复制代码
- 验收项
- 排错表

## Synchronization Checklist

每次阶段推进后同步：

- 当前阶段名与摘要
- 状态 / Roadmap
- 新风险
- 新资源或资产
- 上一期详稿里对下一期的预告是否过时

参数、LUT、类名、材质输入名改名后，做全文搜索确认旧名称没有作为现行说法残留。

## Preserve Existing Work and Defer Destructive Cleanup

- 先检查 dirty worktree；未明确属于本任务的修改一律保留。
- 不主动执行删除文件、删除资产、强制覆盖或历史重写。
- 迁移文档时可保留短小 deprecated stub，避免旧链接立即失效。
- 临时诊断文件集中放到明确的 `_tmp` 目录并使用可检索前缀。
- 确有待清理项时，先搜索下游引用；在最终交付末尾列出绝对路径、类别、引用验证状态和建议命令，由用户决定是否执行。

## Choose the Validation Path Up Front

### Asset-assisted tasks

材质、Blueprint、DataAsset、地图或其他 `.uasset` 需要手工搭建/检查时：

- C++ 编译成功只表示代码阶段完成。
- 给出严格编辑器操作顺序、运行时诊断和视觉验收项。
- 状态写成“代码完成，待资产/视觉验收”，不要提前宣称整阶段完成。

### Asset-free tasks

不需要手工修改资产时，完整闭环应包含：

1. 编译目标并要求明确成功结果。
2. 在 fresh standalone/game process 或目标外部客户端中执行功能。
3. 使用本次运行的独立日志或时间窗口核对唯一成功标识、关键状态与 Error/Warning。
4. 报告启动命令、验证证据、DLL 占用处理以及仍在运行的本任务进程。

不要用旧日志、已加载 Editor 状态或前一次运行残留作为本次证据。

## Delivery Format

一次任务完成后的交付应至少说明：

- 改了哪些文件
- 采用了哪条方案
- 已验证哪些内容
- 还没法验证哪些内容
- 用户下一步在编辑器里要做什么
- 新坑沉淀到哪里
- 是否发生 DLL 占用，处理了哪些本任务进程
- 是否仍有本任务启动的进程运行
- 是否存在待用户手动清理项

如果仍有编辑器手工步骤，按顺序列出：

1. 创建或复制哪个资产
2. 新增哪些参数
3. Inputs / pins / 参数名顺序
4. 哪段代码或配置直接粘贴
5. 资产挂到哪里
6. 日志里应该看到什么
